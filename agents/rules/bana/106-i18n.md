# Internationalisation (i18n)

All user-facing copy is localised (English + Vietnamese) through `useTranslate()` with **typed**
keys. The locale dictionaries are generated — never hand-edited.

## Usage

```typescript
const translate = useTranslate();
// ...
translate('pages.product.title.edit');
translate('pages.restaurant.restaurant.action.select_room');
// with args:
translate('pages.product.product_variant.bundle.description', { variantName });
```

- Keys are typed (`TUseTranslateKeys`) — referencing a non-existent key **fails `tsc`**. Use an
  existing key, or have a new one generated first; do not invent a key inline and expect it to work.
- For `I18nField` label objects coming from the API, render with `getLabelLocale({ label, locale })`
  and read the current locale via `useLocaleState()`.

## Locale files are generated

`apps/core/src/locales/en.ts` and `vi.ts` (3000+ keys each) are **auto-generated** from the
translation source (Google Sheet export). **Never hand-edit them.** To add copy:
1. Add the key + EN/VI to the translation source and regenerate, or hand it to whoever owns the
   export.
2. Only then reference it via `translate(...)`.

If you need a string before the key exists, reuse the closest existing key and flag that a new key
must be generated — don't add it to the locale file manually (it gets overwritten and breaks `tsc`
typing in the meantime).

## Rules
- All copy via `useTranslate()` with typed keys; `tsc` is the guard against typos/missing keys.
- Never hand-edit `apps/core/src/locales/*.ts` — generated.
- New keys go through the translation source + regeneration, not a manual file edit.
- Render API `I18nField` labels with `getLabelLocale` + `useLocaleState`.
- Developer-facing comments stay English ([008](./008-commenting.md)); this rule is for UI copy.
